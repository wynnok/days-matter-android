# 网页端与 Android 共通精进方案

日期：2026-10-06。状态：范围和一致性原则已确认，尚未实施。本文是两端共通能力的唯一规划来源，现阶段统一维护在 Android 仓库；[Android 专属方案](2026-10-06-android-improvement.md) 引用本文，不复制共通规格。

可执行 spec 已发布为 [GitHub Issue #2](https://github.com/wynnok/days-matter-android/issues/2)，标记 `ready-for-agent`。本文保留规划依据与端差异，后续实施和完成验收以该 spec 为准。

## 1. 目标与一致性原则

面向个人及少量长期用户，优先实用与可靠性。两端连接同一 Worker、使用同一账号时，应提供一致的基础能力、业务规则、数据含义和操作结果。

一致性按以下方式执行：

- **能力与规则一致**：事件、分类、资料、站外提醒、账号备份、日期口径及明确的操作反馈不能因客户端不同而改变含义。
- **界面按平台组织**：网页可使用现有工具栏、设置和弹窗；Android 可使用“我的”和二级页面。无需相同导航、布局或逐像素对齐。
- **设备偏好各自保存**：两端都能选择浅色／深色／跟随系统，不代表选择会跨设备同步。本地提醒和桌面配置也不属于账号数据。
- **可分批落地**：记录每端的缺口与验收状态，不能用“一端完成”表示共通能力已经完成。
- **平台能力允许不同**：本地通知权限、设备提醒、Android 桌面小组件和系统后台刷新在专属方案中处理；不要求网页提供相同的系统能力。

“暂时只需要修改 Android”不等于“Android 专属”：例如网页已具备资料保存反馈，Android 补齐它仍属于共通能力。归属由功能含义决定，而非由本次要改哪个仓库决定。

首轮沿用已经确认的范围：管理中心＋轻量摘要，无成就、复杂图表、会员、社区或账号系统重构。已有端功能不因一致化被直接删除；新增范围仍需独立设计和验收。

## 2. 共通能力与两端差异

以下是本地源码核查结果，不是线上或真机验收结果。P0 表示可靠性基础，P1 表示本轮核心能力，P2 表示后续候选。

| 编号 | 共通能力与统一目标 | 网页现状／缺口 | Android 现状／缺口 | 优先级 |
| --- | --- | --- | --- | --- |
| C01 | 日期和近期口径：东八区、已确认发生日期、跨日天数、过期重复状态 | 有跨日／前台检查，但按浏览器本地日期；优先缓存天数，缺字段时会自行推导周期，需要对齐 | 直接使用缓存天数，没有跨日推进，需要对齐 | P0 |
| C02 | 数据与操作反馈：加载、空数据、失败、登录失效及保存结果含义明确 | 资料已有提交防重和保存反馈；其他流程逐项核对 | 资料失败保留输入和成功更新需完善；缓存细节见专属方案 | P0 |
| C03 | 账号数据备份：同一格式与范围，双向导入，追加预览和真实结果 | 有基本 JSON 校验、成功提示；无预览和追加确认，导入后只刷新事件及分类 | 直接选择文件并上传，无预览；导入结果反馈需完善 | P0 |
| C04 | 资料、事件、分类与子事件的基础管理 | 已有相关管理能力；校验及结果与接口核对 | 已有相关管理能力；“我的”补分类入口并复用现有逻辑 | P1 |
| C05 | 站外提醒渠道：配置、启停、测试及事件引用规则 | 已有配置与测试；当前表单缺少渠道启停入口 | 已有配置、启停与测试 | P1 |

网页已有日期分组不等于可操作的时间筛选，两端图标搜索也不等于事件名称搜索。搜索与筛选仍按后续路线图评估，不把已有能力和新增能力混写。

## 3. 共通功能规格

### C01：日期与近期口径

以下规则适用于两端列表、详情和摘要；Android 小组件继承同一规则：

1. 业务日按 **Asia/Shanghai** 划分，天数取日历日之差，不按毫秒差除以 24 小时计算。
2. Worker 确定农历转换和重复事件的发生日期；客户端只推进服务器已确认的公历发生日期所对应的显示天数，不在字段缺失时自行猜测后续周期。
3. 未来日期显示“还有 N 天”，当天显示“今天”；非重复日期过去后显示“已过 N 天”。重复事件的已知日期过去后显示“待同步下一次日期”。
4. 日期缺失或无效显示待同步，不当作零天，也不把日期未知当作没有事件。
5. “近期 7 天”指今天至未来第 6 天，“近期 30 天”指今天至未来第 29 天；不使用“本周／本月”表示滚动窗口。
6. 近期事件只含窗口内已确认的主事件，不含过去事件；每个重复事件按已知一次发生日期计入，不展开多个未来周期。

共通目标是相同业务日、相同账号数据版本下得到相同结果；不承诺两端实时获取彼此的修改。网页的跨日／页面可见性触发与 Android 的生命周期／后台触发可不同。统一展示语义不要求网页新增 Android 的离线缓存或后台常驻能力。

日期权威与客户端展示边界的决策见 [ADR-0002](../adr/0002-cached-occurrence-day-display.md)。网页当前的本地周期兜底也需要在后续实施中核对并对齐，不能视为已经符合该决策。

### C02、C04：管理入口与操作反馈

共通管理能力包括资料、分类、事件、子事件、站外提醒、账号备份、外观和帮助。两端在适合的平台入口提供这些能力；Android 的“我的”布局见专属方案。

资料编辑保留昵称／邮箱：提交中防止重复操作，成功后更新展示，明确失败时保留输入。删除分类或渠道前检查仍在使用它的事件，给出可理解的原因。客户端校验与接口规则一致，不因一端接受了另一端无法表示的数据而破坏基本使用。

所有数据操作区分加载中、成功、明确拒绝、失败或结果未知。未取得数据与确实没有数据分别展示；请求失败不能直接生成“没有事件”。检测到登录失效后要求重新登录，不能把其他账号的内容当作当前账号数据。

联网或可访问网页不等于最新数据已加载。网页不提供离线阅读时应说明连接问题；Android 有缓存时应说明缓存状态。两端均只在成功获取后更新上次成功获取时间；这种时间是客户端新鲜度信息，不代表服务端业务日期。

### C03：账号数据备份与导入

统一称为“账号数据备份”：覆盖分类、事件、子事件和提醒渠道信息，不包含设备偏好、本地提醒或桌面实例。账号资料是否纳入未来备份须另行定义，不从“账号数据”的范围反推当前备份格式。

实施前核对线上格式、版本和渠道凭据覆盖；预览与错误信息不展示凭据值。保留旧格式兼容，同一有效备份应可由任一端导出、另一端导入。

建议流程：

1. 导出前说明范围和格式，操作结果按客户端实际可观察的阶段表达。
2. 导入时先校验格式／版本，预览各类对象数量，说明“追加，不覆盖现有数据，可能产生重复”；用户确认后提交。
3. 提交后刷新所有受影响的账号数据，包括事件、分类和提醒渠道，不能只刷新部分对象。
4. 结果区分明确拒绝、结果未知、请求完成但后续刷新失败、请求与刷新均完成。超时／连接中断可能发生在服务器已写入之后，应先核实数据并说明可能已追加，不直接引导重复提交。

对象预览数量不是实际导入数量。如果接口只有“导入成功”，不能声称精确导入数量、去重或完整回滚。精确报告、去重与事务保证列为后续接口增强。

文件交互按平台处理：网页使用浏览器下载／文件选择，Android 使用系统文件选择与写入。网页只能观察到下载已发起时，不宣称用户已经把文件保存到磁盘；Android 只在实际写入成功后显示保存成功。最近导出记录应说明记录的是发起下载还是实际保存。

### C05：站外提醒渠道

用户入口统一使用“站外提醒”，二级说明它通过 Webhook 提醒渠道发送。两端可配置渠道、启停、测试，并查看事件引用关系；事件引用与渠道启用状态的含义相同。

保留现有参数和测试能力，不建立第二套渠道模型。测试接口成功表示测试请求已完成，不等同于接收端已经送达。本地提醒属于 Android 设备，不与账号渠道合成一个总开关。

### C06：轻量摘要

统一提供事件总数与近期 7 天数量，首页或管理页可以采用不同位置：

- 总数只统计当前账号的主事件，不重复计入子事件，也不受当前分类筛选影响。
- 近期数量遵循 C01 的 7 天窗口；待确认事件不计入，并标明待同步数量。
- 没有可用数据时显示占位，不能用零冒充完整统计。
- 若某端额外保留“今天到期”“全部未来”等统计，应明确标签和范围，不能把它们当作统一的近期数量。

首轮不新增图表、成就体系或统计专用页面。

### C07、C08：外观与帮助

两端均提供浅色、深色、跟随系统，默认跟随系统；用户选择属于当前浏览器或 Android 设备。网页需要补系统模式，Android 复用已有能力。小组件实例的独立外观属于专属方案。

共通帮助解释分类、日期、重复与农历、账号备份、站外提醒及数据状态。各端展示自身版本和适用声明，不用 Android 版本号描述网页版本。通知权限、省电和小组件排查只在 Android 帮助中展开。

## 4. 整体完善的共通后续路线

| 编号 | 候选方向 | 建议范围与纳入条件 |
| --- | --- | --- |
| S01-C | 日期与站外提醒一致性 | 月末、闰年、农历闰月、重复周期和提醒参数回归；以 Worker 规则及测试为准 |
| S02 | 查找与浏览 | 名称搜索、明确的今天／未来／过去筛选；事件数量增加后验证痛点 |
| S03 | 常用场景创建 | 生日、纪念日和目标日期的轻量预填，复用现有事件模型 |
| S04-C | 数据管理增强 | 准确导入报告、去重、事务保证及格式兼容；后端契约先行 |
| S05 | 归档与整理 | 归档和批量移动分类；先明确归档与删除的区别及数据模型影响 |
| S06-C | 通用个性化 | 预设头像、分享卡片等；先确认两端用途及数据归属 |
| S07 | 公开服务保障 | 账号找回／改密／注销、引导和反馈支持；转向公众推广时单独规划 |

这些是候选方向，不是已批准全部实施的需求。设备配置迁移和小组件样式在 Android 专属后续路线中处理。

## 5. 交付与差异管理

先明确 C01–C03 的业务规则、接口和失败语义，再逐端补缺口；C04–C08 可按小批次推进。已有符合目标的端能力复用，避免为了“同一批改动”重复重做。

后续拆任务时，每项 C 编号关联网页、Android、必要的 Worker 工作及验收状态。同一范围可分批交付，暂未对齐的端必须保留差异记录；共通功能只有两端验收完成后才标记完成。核心字段或备份格式需要接口变更时，先保证已有客户端兼容，再实施客户端适配。

## 6. 共通验收

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| CV01 | 同账号、同 Worker，两端成功刷新 | 资料、事件、分类、子事件、渠道数据一致；设备偏好可不同 |
| CV02 | 同数据版本，东八区跨日或客户端处于其他时区 | 发生日期、天数和今天状态一致；刷新触发可不同 |
| CV03 | 重复日期已过、日期缺失或无效 | 两端均显示待同步，不猜测下个周期或当作零天 |
| CV04 | 近期 7／30 天边界、子事件、分类筛选 | 统一窗口、主事件计数；账号摘要不受分类筛选影响 |
| CV05 | 资料成功、明确失败及重复点击 | 防重复提交，成功更新，失败保留输入 |
| CV06 | 两端分别导出，由另一端导入 | 格式兼容、追加范围一致，事件／分类／渠道均正确刷新 |
| CV07 | 无效备份、取消、重复追加、超时及后续刷新失败 | 提交前预览与确认；结果阶段真实，不诱导重复提交 |
| CV08 | 渠道启停、事件引用和测试 | 状态含义一致，不把测试请求成功等同于实际送达 |
| CV09 | 浅色、深色和系统主题变化 | 两端三种模式有效，偏好按设备保存 |
| CV10 | 首次无数据、请求失败、登录失效 | 状态明确，不泄露其他账号内容，不把错误当作空列表 |

跨端验收须记录使用的后端、数据版本和两端版本；不能仅用截图相似证明一致。
