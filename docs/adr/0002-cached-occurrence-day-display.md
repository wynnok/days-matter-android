# 对已确认的发生日期推进显示天数，重复周期仍由 Worker 确定

为了保持网页端与 Android 的日期含义一致，并让 Android 桌面小组件在未打开应用或离线跨日时仍有用，两端客户端可以对 Worker 已确认的公历发生日期，按 Asia/Shanghai 的当前日历日期计算显示天数；农历转换及下一重复周期的发生日期继续由 Worker 确定。非重复事件到期后显示“已过 N 天”，重复事件的已知发生日期过去后显示“待同步下一次日期”，直到同步确认后续日期。

这项规划决策及两端一致性目标已由用户确认，并已通过共通 ticket #4 与 Android ticket #22 实施（2026-10-07）。它取代 [ADR-0001](0001-native-client-and-reminders.md) 中“倒数天数以 Worker 结果为准”对客户端显示的限制，保留其中的发生日期权威、账号数据归属及本地提醒归属边界。两端的刷新触发可按平台不同；统一日期语义不要求网页新增 Android 的离线缓存或系统后台能力。

## 考虑过的方案

- 原样显示同步时的天数：实现简单，但连续几天不打开应用时数字会失真。
- 在 Android 完整推导农历及重复周期：离线能力更强，但需要维护两套日期规则及一致性验证，超出本轮精进范围。
- 只推进已确认日期的显示天数：改善日常阅读，同时保留单一的重复周期规则来源，因此采用此方案。

## 影响

两端列表、详情、摘要及 Android 小组件遵循同一日期展示规则，共通规格维护在[两端共通方案](../plans/2026-10-06-shared-improvement.md)。显示天数从已确认的发生日期计算，不使用“缓存天数减去同步后经过的天数”：Android 现有同步时间是设备记录的请求完成时间，不能代表服务端计算日期。缺少有效发生日期时显示待同步；Android 离线时展示上次成功同步时间，提示其他设备的修改可能尚未获取。

日期推进不表示生成了新提醒，也不表示已获取后续重复周期。小组件在系统允许的刷新机会更新，不承诺零点精确刷新；设备时间变化后重新计算并尝试同步。
